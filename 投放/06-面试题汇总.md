## 1. 业务理解类

### Q1: 解释 CPM、CPC、CPA 的区别，以及各自适用场景

**回答框架**（STAR法）：

```
1. 定义（Situation）
   - CPM：按千次曝光计费
   - CPC：按点击计费
   - CPA：按转化计费

2. 特点对比（Task）
   | 模式 | 风险 | 成本 | 效果 |
   |------|------|------|------|
   | CPM  | 高   | 低   | 不保证 |
   | CPC  | 中   | 中   | 有保证 |
   | CPA  | 低   | 高   | 最保证 |

3. 适用场景（Action）
   - CPM：品牌曝光（可口可乐、宝马）
   - CPC：效果广告（电商、游戏）
   - CPA：直接转化（APP下载、电商下单）

4. 举例说明（Result）
   我在上个项目做电商投放时：
   - 新品发布期：用 CPM 扩大曝光
   - 促销活动期：用 CPC 引流
   - 大促冲刺期：用 CPA 控制成本
   最终 ROI 从 150% 提升到 280%
```

**加分点**：
- 提到 oCPM/oCPC（优化后的计费模式）
- 能说出不同阶段的计费模式选择策略
- 有实际数据支撑

### Q2: 什么是 DSP、SSP、DMP？

**标准答案**：

```
1. DSP（Demand-Side Platform，需求方平台）
   - 定义：为广告主提供投放服务
   - 功能：广告创建、定向投放、自动出价、效果监控
   - 典型平台：巨量引擎、腾讯广告、Google Ads

2. SSP（Supply-Side Platform，供给方平台）
   - 定义：为媒体提供流量变现服务
   - 功能：流量管理、收益优化、广告控制
   - 典型平台：Google AdSense、百度联盟

3. DMP（Data Management Platform，数据管理平台）
   - 定义：用户数据管理和分析
   - 功能：用户画像、人群定向、Look-alike
   - 数据维度：人口属性、兴趣标签、行为数据

4. 关系
   广告主 → DSP → Ad Exchange ← SSP ← 媒体
                     ↑
                    DMP（提供数据支持）
```

### Q3: 广告竞价的基本流程是什么？

**详细回答**：

```
流程（< 100ms 完成）：

1. 用户触发请求（10ms）
   - 用户访问网站/APP
   - SSP 发起广告请求

2. 召回候选广告（30ms）
   - 根据用户画像（地域、年龄、兴趣）
   - 召回 100+ 个候选广告

3. 粗排（10ms）
   - 快速过滤不符合条件的广告
   - 筛选出 20 个广告

4. 精排（30ms）
   - 计算综合得分 = 出价 × 质量分
   - 质量分 = f(预估CTR, 预估CVR, 广告质量, 落地页体验)

5. 竞价和扣费（10ms）
   - 使用 GSP（广义第二价格）
   - 最高得分获胜
   - 实际支付 = (第二名得分 / 自己质量分) + 0.01

6. 返回广告（10ms）
   - 展示广告
   - 记录曝光和消耗
```

**代码示例**：
```javascript
// 竞价逻辑（简化版）
const bids = [
  { advertiser: 'A', bid: 10, quality: 0.9 },  // 得分 9.0
  { advertiser: 'B', bid: 8, quality: 1.0 },   // 得分 8.0
  { advertiser: 'C', bid: 6, quality: 0.8 }    // 得分 4.8
]

// 排序后 A 获胜
const winner = bids[0]  // A
const secondScore = bids[1].bid * bids[1].quality  // 8.0
const actualCost = (secondScore / winner.quality) + 0.01
// A 实际支付 = 8.0 / 0.9 + 0.01 = 8.89 元（而不是 10 元）
```

**加分点**：
- 了解 GSP 和 VCG 竞价算法
- 能解释质量分的计算逻辑
- 知道实时竞价的性能优化方法

### Q4: 如何做广告效果归因？

**回答框架**：

```
1. 归因模型（5种）

   ① 首次点击归因
   - 转化归功于第一个接触点
   - 适用：品牌广告

   ② 末次点击归因
   - 转化归功于最后一个接触点
   - 适用：效果广告（最常用）

   ③ 线性归因
   - 所有接触点平均分配
   - 适用：多渠道协同

   ④ 时间衰减归因
   - 越接近转化时间权重越高
   - 适用：长决策周期

   ⑤ 数据驱动归因
   - 机器学习自动计算贡献度
   - 适用：数据量大的情况

2. 实际案例
   用户转化路径：
   Day 1: 搜索广告（首次接触）
   Day 3: 信息流广告
   Day 5: 直接访问 → 转化

   不同归因结果：
   - 首次点击：100% 归功于搜索广告
   - 末次点击：100% 归功于直接访问
   - 线性：各 33.3%
   - 时间衰减：搜索 20%、信息流 30%、直接 50%

3. 技术实现
   - 数据埋点（曝光、点击、转化）
   - Cookie/设备ID 追踪
   - 归因窗口（通常 7-30 天）
```

**代码示例**：
```typescript
interface TouchPoint {
  channel: string
  time: Date
  type: 'impression' | 'click'
}

// 线性归因
function linearAttribution(touchPoints: TouchPoint[], revenue: number) {
  const attribution = touchPoints.map(tp => ({
    channel: tp.channel,
    credit: revenue / touchPoints.length
  }))
  return attribution
}

// 时间衰减归因
function timeDecayAttribution(touchPoints: TouchPoint[], revenue: number) {
  const now = new Date()
  const weights = touchPoints.map(tp => {
    const days = (now.getTime() - tp.time.getTime()) / (1000 * 60 * 60 * 24)
    return Math.exp(-days / 7)  // 7天半衰期
  })
  const totalWeight = weights.reduce((a, b) => a + b, 0)
  
  return touchPoints.map((tp, i) => ({
    channel: tp.channel,
    credit: (weights[i] / totalWeight) * revenue
  }))
}
```

### Q5: 什么是 Look-alike（相似人群扩展）？

**标准答案**：

```
1. 定义
   - 基于种子人群（高价值用户）
   - 找出相似特征的新用户
   - 扩大目标人群规模

2. 原理
   种子人群特征：
   - 年龄：25-35岁
   - 地域：一线城市
   - 兴趣：科技、游戏
   - 行为：浏览过数码产品
   
   机器学习模型：
   - 提取特征向量
   - 计算相似度
   - 筛选相似用户

3. 应用场景
   电商案例：
   - 种子人群：1万个付费用户
   - 相似度阈值：0.8
   - 扩展倍数：10倍
   - 结果：10万个潜在用户
   
   效果：
   - 转化率：与种子人群相近
   - 覆盖人数：扩大 10 倍
   - ROI 提升：30%

4. 技术实现
   - 特征工程：提取用户特征
   - 相似度计算：余弦相似度、欧氏距离
   - 模型：协同过滤、深度学习
```

**代码示例**：
```python
# 简化版 Look-alike（余弦相似度）
from sklearn.metrics.pairwise import cosine_similarity

# 种子用户特征
seed_users = [[25, 1, 1, 0, 1],  # [年龄(归一化), 一线城市, 科技兴趣, ...]
              [28, 1, 1, 1, 1],
              [30, 1, 0, 1, 1]]

# 候选用户特征
candidate_users = [[26, 1, 1, 0, 1],  # 相似度高
                   [45, 0, 0, 0, 0],  # 相似度低
                   [27, 1, 1, 1, 1]]  # 相似度高

# 计算相似度
similarity = cosine_similarity(candidate_users, seed_users)
avg_similarity = similarity.mean(axis=1)

# 筛选相似用户（阈值 0.8）
lookalike_users = [i for i, sim in enumerate(avg_similarity) if sim > 0.8]
```

### Q6: 如何设计一个复杂的投放表单？

**回答框架**：

```
1. 需求分析
   - 层级：广告计划 → 广告组 → 广告创意（3层）
   - 字段：50+ 个字段
   - 联动：定向条件、出价策略、预算分配
   - 校验：前端校验 + 后端校验

2. 技术选型
   - 表单库：Formily（推荐）/ React Hook Form
   - 理由：
     ✅ 支持复杂联动逻辑
     ✅ 支持动态表单
     ✅ 支持异步校验
     ✅ 性能好（虚拟 DOM）

3. 核心功能实现

   ① 表单联动
   - 出价类型变化 → 出价金额显示/隐藏
   - 预算变化 → 校验是否超过账户余额
   - 定向条件变化 → 实时预估覆盖人数

   ② 复杂组件
   - 地域选择：省/市/区 三级联动
   - 兴趣选择：树形多选，支持搜索
   - 创意上传：图片预览、裁剪、压缩

   ③ 性能优化
   - 字段过多：分步表单（Step）
   - 联动复杂：防抖/节流
   - 校验耗时：异步校验 + Loading

4. 代码示例（见下方）
```

**代码示例**：
```tsx
import { createForm, onFieldValueChange } from '@formily/core'

const form = createForm({
  effects() {
    // 联动1：出价类型变化
    onFieldValueChange('bidding.type', (field) => {
      form.setFieldState('bidding.amount', (state) => {
        state.display = field.value === 'auto' ? 'none' : 'visible'
      })
    })
    
    // 联动2：预算校验
    onFieldValueChange('budget', async (field) => {
      const balance = await getAccountBalance()

        field.setErrors(['预算超过账户余额'])
      }
    })
    
    // 联动3：预估覆盖人数
    onFieldValueChange('targeting.*', debounce(async () => {
      const targeting = form.values.targeting
      const reach = await estimateReach(targeting)
      form.setFieldState('reach', (state) => {
        state.value = reach
      })
    }, 500))
  }
})
```

### Q7: 如何优化 10万+ 数据的表格渲染？

**标准答案**：

```
问题现象：
- 10万行数据，渲染卡死
- 滚动卡顿
- 内存占用过高（OOM）

优化方案（4个层次）：

1. 虚拟滚动（最重要）
   - 原理：只渲染可视区域的行
   - 10万行 → 实际渲染 20 行
   - 库：react-window / react-virtualized
   - 效果：渲染时间 10s → 0.5s

2. 分页加载
   - 服务端分页：每次加载 20 条
   - 无限滚动：滚动到底部加载更多
   - 优点：减少首屏数据量

3. 字段优化
   - 按需渲染：隐藏不必要的列
   - 懒加载图片：进入视口再加载
   - 格式化优化：避免复杂计算

4. Web Worker
   - 数据处理（排序、过滤）放到 Worker
   - 主线程只负责渲染
   - 避免阻塞 UI
```

**代码示例**：
```tsx
import { VariableSizeList } from 'react-window'
import AutoSizer from 'react-virtualized-auto-sizer'

// 虚拟滚动表格
const VirtualTable: React.FC<{ data: any[] }> = ({ data }) => {
  const Row = ({ index, style }: any) => {
    const item = data[index]
    return (
      <div style={style} className="table-row">
        <div className="cell">{item.name}</div>
        <div className="cell">{item.impressions.toLocaleString()}</div>
        <div className="cell">{item.clicks.toLocaleString()}</div>
        <div className="cell">{item.ctr.toFixed(2)}%</div>
      </div>
    )
  }
  
  return (
    <AutoSizer>
      {({ height, width }) => (
        <VariableSizeList
          height={height}
          width={width}
          itemCount={data.length}
          itemSize={() => 50}      // 每行高度
          overscanCount={5}        // 预渲染 5 行
        >
          {Row}
        </VariableSizeList>
      )}
    </AutoSizer>
  )
}
```

### Q8: 如何实现实时的广告监控大盘？

**回答框架**：

```
需求：
- 数据实时更新（< 1s 延迟）
- 100+ 个图表同时显示
- 数据准确无误

技术方案：

1. 实时通信（3种方案）

   ① WebSocket（推荐）
   - 双向通信
   - 服务端主动推送
   - 适合高频更新
   
   ② Server-Sent Events (SSE)
   - 单向推送
   - 自动重连
   - 适合只接收数据
   
   ③ 轮询
   - 定时请求
   - 简单但延迟高
   - 不推荐

2. 图表性能优化

   ① 懒加载
   - 进入视口才渲染
   - 使用 Intersection Observer
   
   ② 降采样
   - 100万个数据点 → 显示 1000 个点
   - 不影响视觉效果
   
   ③ Canvas 渲染
   - ECharts 使用 Canvas
   - 比 SVG 性能更好
   
   ④ Web Worker
   - 数据计算放到 Worker
   - 主线程只负责渲染

3. 数据管理
   - 使用 Redux/Zustand 管理状态
   - 实时数据增量更新（不是全量替换）
   - 数据缓存（避免重复计算）
```

**代码示例**：
```tsx
// WebSocket 实时数据
class RealtimeClient {
  private ws: WebSocket
  
  connect(onMessage: (data: any) => void) {
    this.ws = new WebSocket('wss://api.example.com/realtime')
    
    this.ws.onmessage = (event) => {
      const data = JSON.parse(event.data)
      onMessage(data)
    }
    
    // 心跳保活
    setInterval(() => {
      if (this.ws.readyState === WebSocket.OPEN) {
        this.ws.send(JSON.stringify({ type: 'ping' }))
      }
    }, 30000)
  }
}

// React 组件
const RealtimeDashboard: React.FC = () => {
  const [metrics, setMetrics] = useState({
    impressions: 0,
    clicks: 0,
    cost: 0
  })
  
  useEffect(() => {
    const client = new RealtimeClient()
    client.connect((data) => {
      // 增量更新
      setMetrics(prev => ({
        impressions: prev.impressions + data.impressions,
        clicks: prev.clicks + data.clicks,
        cost: prev.cost + data.cost
      }))
    })
  }, [])
  
  return (
    <div>
      <MetricCard title="曝光" value={metrics.impressions} />
      <MetricCard title="点击" value={metrics.clicks} />
      <MetricCard title="消耗" value={metrics.cost} />
    </div>
  )
}
```

- 知道大数据量图表的优化方法

5. 首屏优化
   - SSR（服务端渲染）

### Q13: 你在投放系统中遇到的最大挑战是什么？

**回答示例**：

```
【挑战】
监控大盘的性能问题 —— 100+ 图表同时渲染导致页面卡死

【背景】
- 监控大盘有 120 个 ECharts 图表
- 每个图表包含 1000-10000 个数据点
- 用户打开页面后，浏览器直接崩溃

【分析】
1. Chrome DevTools 分析：
   - 初始渲染耗时：15s+
   - 内存占用：2.5GB（触发 OOM）
   - 主线程阻塞严重

2. 根因：
   ① 所有图表同时渲染
   ② 数据量过大（120万个数据点）
   ③ 渲染和数据计算都在主线程

【解决方案】

方案1：懒加载（最有效）
- 使用 Intersection Observer
- 只渲染可视区域的图表（约 6 个）
- 滚动到才渲染
- 效果：初始渲染 120 个 → 6 个，速度提升 95%

方案2：图表降采样
- 1万个点 → 显示 500 个点
- 使用 Largest-Triangle-Three-Buckets 算法
- 不影响视觉效果
- 效果：渲染时间减少 80%

方案3：Web Worker
- 数据聚合、排序、过滤放到 Worker
- 主线程只负责渲染
- 效果：主线程不再阻塞

方案4：Canvas 渲染
- ECharts 使用 Canvas 而不是 SVG
- Canvas 性能更好（尤其是大数据量）

【结果】
- 首屏加载：15s → 1.5s（提升 90%）
- 内存占用：2.5GB → 200MB（减少 92%）
- 滚动 FPS：< 10 → 60（丝滑）
- 用户满意度：2分 → 4.5分

【收获】
1. 技术：掌握了大数据量渲染的优化方法
2. 思维：学会了性能分析和定位的方法论
3. 业务：理解了用户体验的重要性
```
